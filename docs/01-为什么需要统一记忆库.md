# 01 · 为什么需要统一记忆库

## 问题：AI 工具的记忆是碎片化的

2026 年下半年，一个重度 AI 协作用户的工具箱里往往同时有：Claude Code、Codex CLI、Cursor、Cline、Gemini CLI、Trae、Qoder，以及各类国产 IDE / 客户端。它们每家都在发展自己的"记忆"：

- **项目级**：`.claude/`、`.workbuddy/memory/`、`.trae/`、`.agent/`、`AGENTS.md`……
- **用户级**：`~/.claude/`、`~/.codex/`、`~/.workbuddy/MEMORY.md`……
- **强制注入的 auto-memory**：某些工具的 harness 会强制把会话摘要写进自己的记忆目录，没有开关。

结果是三重碎片化：

1. **跨工具失忆**——在 A 工具里踩过的坑、定下的约定，切到 B 工具全部归零，B 会用另一种方式把同一个坑再踩一遍。
2. **跨会话失忆**——同一家工具的记忆常常只覆盖"上一个会话"，更早的决策、更早的偏好，需要靠用户在对话里复述。
3. **不可审阅**——记忆散落在工具私有目录、私有格式里，用户既看不到 AI"记了什么"，也无法批量修正错误记忆。

还有一个隐性问题：**工具私有记忆位里的记忆，质量无法保证**。AI 在会话末尾匆忙写的摘要，可能包含错误结论、过期路径、把"本次会话的临时决定"当成"长期约定"。

## 方案选型：为什么是 Obsidian

要求很朴素：

| 需求 | 为什么 |
|---|---|
| **任何工具都能读写** | Markdown 纯文本 + 本地文件系统，所有 CLI / IDE / 网页端都能通过文件操作触达 |
| **人能直接审阅** | 用户自己天天在用的笔记软件，打开就能看、能改 |
| **结构化但不僵死** | 文件夹即层级、frontmatter 即元数据、wiki 链接即关联，不需要数据库 |
| **私有且可备份** | 本地文件，git / 网盘 / Obsidian 快照各管一摊 |
| **已有生态** | 模板（Templater）、检索（Obsidian 自带）、可视化（Dataview / 自研插件）都是现成的 |

Obsidian 库恰好全部满足。于是定下第一铁律：

> **记忆唯一落点：Obsidian 记忆库。禁止写入任何工具私有记忆位。工具的系统提示 / 自定义指令里只放"指针 + 铁律短钩子"。**

## 工具位不是不能写，是只能写"门牌"

严格说，完全禁止碰工具位做不到也不必要——各工具总得有个地方被告知"记忆库在哪"。所以边界划在内容类型上：

- ✅ 工具位可以放：**指向记忆库的入口指针**、**铁律短钩子**（告诉 AI"写记忆前先读哪个文件"）
- ❌ 工具位不能放：任何具体的偏好、决策、教训、项目事实——那些是**记忆内容**，一律落 Obsidian

判据一句话：**工具位里只准放门牌，不准放货物。**

## auto-memory 这类"关不掉"的写入怎么办

有些工具的 auto-memory 由 harness 强制写入，无开关可关。与其写一条"必须关掉"的做不到的铁律（恒红门禁同族），不如给它一个明确定性：

> **影子层**——只当缓存看：不作落点、不作证据、不算"已查过同名"；需要跨会话存活的事实必须**同轮**落 Obsidian；影子层有而 Obsidian 无正本的内容 = 待搬材料（单向搬入，不做双向同步）。

这套"三条处置口径"让强制写入变得无害：它写它的，正本永远在 Obsidian，冲突一律以 Obsidian 为准。
