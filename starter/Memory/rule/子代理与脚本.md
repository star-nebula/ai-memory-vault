# 子代理与上下文 / 操作脚本 / 版本管理（Rule 分节）

> **派发子代理 / 修改 `scripts\` / 版本与守卫问题时读本文件。**

## 子代理与上下文（防规则失联）

- **派发子代理/子任务**时,父会话必须把「记忆库铁律」或至少记忆库入口（工作区根 `Memory/`）写入子代理指令;子代理收尾时须询问用户或回传「是否需落记忆库」,不得静默跳过。
- 上下文被压缩/很长时,规则细节可能丢失——此时以「读 `Rule.md` 目录页定位后读对应分节」为准,不要凭记忆猜。
- 若完成重要工作但上下文里完全没有记忆库入口(例如工具未注入 AGENTS.md),应主动询问用户「是否记入记忆库」,而非当作不存在。
- **子代理派发透传模板**(原样粘贴进子代理指令开头,保证入口不丢不旧):

  > 记忆库位于工作区根 `Memory/`(权威规则 = `Rule.md` 目录页 + `rule\` 分节文件,写前先按操作读对应分节;结构与读取路由见 `_index.md`)。
  > 当前项目名:`<项目名>`。
  > 你的第一动作:Read `Memory\Rule.md`(目录页)并按其中映射读对应分节文件,回传一句确认;完成重要工作须回传「是否需落记忆库」。
  > 若你被限制为只读子代理:发现需落库内容时不得静默,须在回传中显式列出待落库条目,由父会话代写。

## 操作脚本（工作空间约定，非记忆）

脚本统一放工作空间根目录 `scripts\`(没有则创建);每新增或修改脚本,同步更新其 `README.md`(脚本名、功能、调用方式与示例),保证任何 agent 仅凭 README 可直接调用。脚本的用途、经验等跨会话信息按记忆规则落入 `Projects\<项目名>\` 或 `Lessons\`。

## 版本管理

**记忆库内不建 `.git`**——记忆层与公开内容共用仓库时,私密笔记有被误推上公开远端的尾部风险,靠两层守卫:

1. `.gitignore` 忽略记忆层(从源头不入库);
2. 父仓 `pre-commit` 钩子**顶部**守卫:任何触碰 `Memory/` 的提交一律拒绝(防 `git add -f` 与未来误配置)。钩子不在版本库内,换机器需手工恢复——恢复方法要文档化。

若确需给记忆层做版本回溯,优先用 Obsidian 自带文件快照 / 文件历史插件;建独立本地 git 仓的收益(历史检索)通常不敌维护成本,且嵌套仓会被父仓判为嵌入式仓库。
